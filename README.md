# 技术洞察（tech-insight）

> 本仓库按 **公司 / 实验室** 分文件夹，收录 AI 技术点的**技术洞察**：每个技术点一份独立文档 + 一个同名资料文件夹；每家公司一个文件夹 + 一份该公司自己的总览 README。
> **收录状态**：**1 家公司 / 5 个技术点 / 42 张图表 / 12 份调研笔记**（截至 2026-10-14）
> **时间口径**：一律采用 **arXiv v1 首次投稿时间**（UTC）。

---

## 一、仓库结构

```
tech-insight/
├── README.md                        ← 本文件：仓库总览与公司索引
├── .agents/skills/tech-insight/      ← 产出这些洞察的 skill（SKILL.md）
└── <公司或实验室>/                    ← 一级分类：一家一个文件夹
    ├── README.md                    ← 该公司的技术洞察总览（逐项摘要 + 时间线 + 横向对比）
    ├── <公司>-<技术点>-技术洞察.md    ← 每篇洞察（三章 + 三附录）
    └── <技术点缩写>-<技术点名>/        ← 该技术点的资料
        ├── research/                ← 调研笔记（逐条附来源链接，不放原始抓取件）
        └── assets/                  ← mermaid 源文件 mmd/ · 渲染产物 svg/ png · 预览.html
```

**一句话读法**：先看本文件选公司 → 进该公司 `README.md` 看技术点一览 → 挑一篇洞察读它的 `TL;DR` 表与「技术影响」章 → 需要核实细节时进 `research/` 看原始笔记与来源链接。

## 三、每篇洞察的统一结构

所有洞察文档遵循同一骨架，**便于横向对比与快速定位**：

| 章节 | 内容 |
| --- | --- |
| **0. 结论速览（TL;DR）** | 表格：技术定位 / 核心洞察 / 关键机制 / 效果 / 代价 / 热度 / 影响 / 变种 / 关键判断 |
| **1. 技术背景** | 业界在什么场景下遇到什么问题（**每个场景给量化证据**）+ 问题图谱（mermaid）+ 要点一览表 |
| **2. 技术介绍** | 一句话定义 → 机制逐条（公式 + 伪代码 + 超参）→ **UML 类图** → **UML 时序图** → 实现细节 → 实验数字 → 论文自陈局限 |
| **3. 技术影响** | 影响力坐标系 → 影响逐条 → **变种技术（已出现）** → **变种技术（方向预测）** → 风险与不确定性 → 对研发团队的启示 |
| **附录 A** | 参考资料（分类表格，每条带链接） |
| **附录 B** | 术语表 |
| **附录 C** | 事实、推测与资料核查（含"不可外推的边界"与"未找到"清单） |

图表统一用 **mermaid**（`flowchart` / `classDiagram` / `sequenceDiagram` / `stateDiagram-v2` / `xychart-beta`），源文件保留在各自 `assets/mmd/`，渲染产物同时提供 SVG 与 PNG，另有自包含的 `预览.html` 便于连续浏览。

## 四、质量约定（读这些文档时可以预期的标准）

1. **事实与推测分离**：正文中的推断一律标注"（推测）"，并在附录 C 汇总分界。
2. **"未找到"必写**：查不到就显式写"未找到"——例如"论文无 32K/128K 实验""无官方代码""vLLM 集成未找到证据"。**不臆造数字**。
3. **引用要带坐标系**：不只给绝对值，还给对照（例：138 篇引用 vs MInference 487 / NSA 551）。
4. **反证必须收录**：第三方独立复现或批评写入"风险与不确定性"，并**注明其前提条件**。
5. **论文内部不一致要标**：表格均值与分项对不齐、正文公式与附录代码不一致、摘要与正文口径不一致，全部记录并注明引用时以哪个为准。
6. **区分论文自陈与理论值**：厂商口径（如吞吐 −4.6%）与理论值（FLOPs +0.5%）分开列。
7. **不夸大落地**：明确区分"学术影响"与"工程落地"两层；没有生产模型背书就写"无生产模型背书"。
8. **数字可复算**：关键数字可回溯到论文表号/节号；换算得来的要标注"由表 X 换算，非论文原值"。
9. **不留原始抓取件**：调研完成后清理网页/PDF 等 raw 文件，**只保留笔记中的来源链接**（链接已固化在 `research/`）。

## 五、如何扩展

本仓库的洞察由 agent 依据 **tech-insight skill** 产出（位于 [`.agents/skills/tech-insight/SKILL.md`](.agents/skills/tech-insight/SKILL.md)），流程固定为：核实技术点身份与归属 → 按公司建目录 → 并行调研（子代理落盘笔记）→ 一手精读原文 → 撰写三章文档 → 渲染校验 mermaid → 生成预览页 → 清理 raw → 更新总览。

| 想做的事 | 怎么说 |
| --- | --- |
| 新增一个技术点 | "帮忙洞察 XXX 技术点"（已有公司会自动复用其文件夹；新公司会自动新建并生成该公司的 README） |
| 维护总览 | 新增技术点后 agent 会自动更新该公司 `README.md`；新增公司时会同时更新本文件的索引表 |
| 只要核查不要文档 | "XXX 这个技术点是否真实存在 / 属于哪家" |

**新增一家公司时需同步三处**：① 新建 `<公司>/` 文件夹与 `<公司>/README.md`；② 在本文件 §二的索引表加一行；③ 技术点文档与资料文件夹按 §一 的结构放置。
