# 技术洞察（tech-insight）

把"一个技术点"变成"一份可交付、可核查、可复用的技术洞察 md"。本 skill 是多个洞察任务沉淀下来的固定流程，**照做即可，不要重新发明结构**。

---

## 0. 产出定义（先对齐预期）

一次"洞察"至少交付：

1. **一份主文档**：`<技术点前缀>-<技术点>-技术洞察.md`（放在对应公司文件夹下）
2. **一个同名文件夹**：`<技术点缩写>-<技术点名>/`
   - `research/`：调研笔记（每篇 1–3 份，逐条附 URL）
   - `assets/`：mermaid 源文件 `mmd/`、渲染产物 `svg/ png`、`预览.html`
3. **总览更新**：把新技术点补进该公司文件夹下的 `<公司>-技术洞察总览.md`（不存在就创建）
4. **raw 清理**：不留任何原始抓取件

主文档固定七段：`0 结论速览(TL;DR)` → `1 技术背景` → `2 技术介绍` → `3 技术影响` → `附录 A 参考资料` → `附录 B 术语表` → `附录 C 事实、推测与资料核查`。

---

## 1. 第一步：识别与可行性核查（Gate，不可跳过）

**在写任何正文之前**先核实三件事，并把结论写进回复：

1. **技术点是否真实存在**：找到至少一个一手来源（arXiv abs 页 / 官方仓库 / 官方文档 / 官方博客）。
2. **归属是否正确**：确认是哪个公司/实验室/团队。注意常见错配——论文正文写的机构、开源组织名、以及"作者个人所属机构"可能是三个不同的东西（例：一作属高校、公司作者属厂商、开源仓库挂在公司 Seed 组织下）。
3. **术语是否多义**：同一个词在不同语境可能指完全不同东西。**必须显式澄清你在写哪个**，例如：
   - "flex attention" → PyTorch `torch.nn.attention.flex_attention`（通用框架）vs FlexPrefill（具体算法）
   - "swa" → 全层滑窗 / 层间混合滑窗 / token 类型分化滑窗（三者正交）
   - "shemem" → 很可能是 shmem（单边通信），不是拼写错误就照原文
   - "triton-dist" → 通常指 ByteDance-Seed/Triton-distributed

**若查不到强相关来源**：直接反馈"**未找到与该技术点强相关的来源，可能不存在或名称有误**"，并给出你检索过的关键词与候选；**不要硬凑一篇洞察**。

**核实 arXiv 编号**：搜索结果的编号经常错。必须打开 abs 页确认标题、作者、日期一致后才引用。历史踩坑：`2502.12962`（不是 Over-Tokenized）、`2503.20495`（不是 UB-Mesh）、`2406.16801`（不是 LoongTrain）、`2112.06930`（不是 NVSHMEM）。

## 2. 目录与命名（按公司/实验室分类）

```
<工作区根>/
└── <公司或实验室>/                      ← 一级分类：一家一个文件夹
    ├── <公司>-技术洞察总览.md            ← 该公司所有技术点的总览
    ├── <公司>-<技术点>-技术洞察.md       ← 每篇洞察
    ├── <技术点缩写>-<技术点名>/          ← 每个技术点一个文件夹
    │   ├── research/                    ← 调研笔记（只放笔记，不放抓取件）
    │   └── assets/                      ← mmd/ svg/ png/ 预览.html
    └── Overview-总览/                    ← 总览的图表资产（如总览时间线图）
```

规则：
- **一级目录 = 公司/实验室**（`ByteDanceSeed/`、`DeepSeek/`、`Alibaba-Qwen/`、`Moonshot/` …）。已有公司文件夹就直接复用，**不要重复建**。
- 技术点文件夹命名用 `<缩写>-<全名>`（如 `VWN-Virtual-Width-Networks`、`OE-Over-Encoding`）。
- 文档 vs 文件夹：文档在**公司文件夹根**，资产在**技术点文件夹内**。
- 每篇文档的 TL;DR 下方加一行「**目录与流程约定**」，把上面三条写进去，保持系列自述一致。

## 3. 并行调研：子代理编排

**每个技术点起 2–3 个子代理**（不要自己串行检索，太慢），建议切分：

| 子代理 | 任务 |
| --- | --- |
| A | **机制精读**：一手论文全文 + 官方仓库，逐节核实公式、超参、算法、实验数字、代码级细节 |
| B | **技术背景**：该问题的量化痛点（要有硬数字）、既有路线及其硬伤、谱系与代表工作编号 |
| C | **技术影响**：开源/热度/引用数、产业落地证据、后续工作与变种、公开质疑与反证 |

子代理 prompt 必须包含这四条硬约束：

1. **落盘路径写死**：`<公司>/<技术点文件夹>/research/<名>-调研笔记.md`；**禁止在工作区其他位置创建文件**；临时文件放 `/tmp` 并清理。
2. **回复 ≤25–30 行**：详细内容只写文件，回复只给要点摘要（省主上下文）。
3. **每条事实附 URL**，并标注 `【事实】/【推测】/【未找到】`；**找不到就明确写"未找到"，禁止臆造数字**。
4. **纠错义务**：若发现任务书里的编号/归属/数字有误，必须在回复开头单独列出。

派活后**不要空等**：自己去读一手材料（第 4 步）。

---

## 4. 一手精读：自己读原文

子代理负责广度，**你负责一手精度**。至少要亲自拿到：

- **论文全文**：`curl -sL -A "Mozilla/5.0" https://arxiv.org/html/<id>v<n> -o p.html`，再用 python 去标签抽正文，**分段打印**（控制输出量）。ar5iv 可作交叉核对。
- **官方仓库**：`curl -s https://api.github.com/repos/<org>/<repo>` 取 star/fork/创建与推送时间；`.../git/trees/main?recursive=1` 取文件树（**据此核实算子/文件名**，不要凭印象）。
- **官方文档**：readthedocs / 官方博客。
- **提交历史**：abs 页的 `Submission history` 拿 **v1 首次投稿时间**（写文档与总览都用这个口径）。

## 5. 文档结构模板

```markdown
# <公司/团队> <技术点名>（<英文名/缩写>）技术洞察

> **洞察对象**：论文全名（arXiv:xxxx.xxxxx，v1 日期 / 最新版日期，会议）
> **代码**：仓库链接（License，star 数）
> **团队/作者**：核实后的归属（注意区分高校/公司/开源组织）
> **文档版本**：YYYY-MM-DD
> **系列关系**：本报告是"<公司>技术洞察"系列的第 N 篇（列前序链接）
> ⚠️ **术语澄清**：若该词有多义，在此写明本报告指哪一个
> **目录与流程约定**：…（见 §2）

## 0. 结论速览（TL;DR）      ← 表格：定位/核心洞察/机制/效果/代价/热度/影响/变种/关键判断

## 1. 技术背景：业界在什么场景下遇到什么问题
### 1.1–1.5 场景一…五           ← 每个场景给量化证据，不要定性空谈
### 1.6 问题图谱（mermaid flowchart）
### 1.7 背景要点一览（表格：场景/具体问题/既有对策/残留缺口）

## 2. 技术介绍
### 2.1 一句话定义与核心洞察
### 2.2+ 机制逐条（公式 + 代码/伪代码 + 超参）
### 类图（UML classDiagram，对应官方实现/伪代码）
### 时序图（UML sequenceDiagram，走一遍前向/通信流程）
### 实现细节与工程取舍（表格：超参论文值 vs 代码默认值）
### 实验数字（逐条给出处：表号/节号）
### 论文自陈的局限 + 论文内部瑕疵（表格均值对不齐、公式符号歧义等）

## 3. 技术影响：对业界意味着什么，会不会出现变种技术
### 3.1 影响力的坐标系（同行评审/开源/热度/引用数/生态，**引用数要带坐标系**）
### 3.2–3.4 影响逐条
### 3.5 变种技术（一）：已经出现（表格，每行给证据链接）
### 3.6 变种技术（二）：可能的下一批方向（表格：方向/核心想法/支撑证据/受益场景/风险）
### 3.7 风险与不确定性
### 3.8 对研发团队的启示（表格：优先级/建议/理由，结合用户实际技术栈）

## 附录 A. 参考资料          ← 分类表格，每条带链接
## 附录 B. 术语表
## 附录 C. 事实、推测与资料核查
### C.1 事实与推测的分界
### C.2 本次修正与澄清（含"不可外推的边界"与"论文内部不一致"）
### C.3 调研支撑文件（工作区内路径）
```

## 6. 写作硬规则

1. **事实/推测分离**：正文凡推断必写"【推测】"或"（推测）"；附录 C 汇总分界。
2. **"未找到"要显式写**：比"含糊带过"有价值得多。例如"论文无 32K/128K 实验""未找到官方代码""vLLM 集成未找到证据"。
3. **引用要带坐标系**：不要只写"138 篇引用"，要写"138 篇（对照 MInference 487 / NSA 551）"——绝对值无意义。
4. **反证必须收录**：第三方独立复现/批评要写进 §3.7，并带上其**前提条件**（例："在 τ=0、即关闭该分支的条件下"）。
5. **论文内部不一致要标**：表格均值与分项对不齐、正文公式与附录代码不一致、摘要与正文口径不一致——全部记录，并注明引用时以哪个为准。
6. **区分"论文自陈"与"我方推断"**：厂商口径（如吞吐 −4.6%）与理论值（FLOPs +0.5%）要分开列。
7. **不夸大落地**：区分"学术影响"与"工程落地"两层；没有生产模型背书就写"无生产模型背书"。
8. **数字可复算**：写进正文的关键数字要能由表号/节号回溯；换算来的要标"由表 X 换算，非论文原值"。

## 7. Mermaid 图表与渲染校验（必做）

**图型选择**：`flowchart` 问题图谱/数据流 · `classDiagram` 类结构（对应官方实现）· `sequenceDiagram` 时序 · `stateDiagram-v2` 状态机 · `xychart-beta` 曲线（缩放律/权衡曲线）。

**固定渲染命令**（本环境的本地管线，勿另装）：

```bash
MMDC=/home/jiali/codes/agent_workspace/mermaid-render/node_modules/.bin/mmdc
PC=/home/jiali/codes/agent_workspace/mermaid-render/puppeteer-config.json
$MMDC -p $PC -i assets/mmd/<name>.mmd -o assets/<name>.svg -b white
$MMDC -p $PC -i assets/mmd/<name>.mmd -o assets/<name>.png -b white -s 3
```

用一段 python 脚本**从 md 里抽取全部 mermaid 块 → 逐块写 `.mmd` → 逐块渲染**，任何 FAIL 都要修到 0；渲染成功即语法有效（不必看图，本环境模型可能无法读图）。

**已知语法坑**：
- **绝不要在 `["..."]` 标签内使用裸双引号**（`\"` 也不行）→ 用中文引号「」。这是最常见的 parse error 来源。
- 节点文本里的 `|`、`{`、`}` 需避免或改写。
- `xychart-beta` 的 `x-axis` 标签数组长度要与数据点数一致。
- 图内文字用 `<br/>` 换行；`style X fill:#ffe9b0` 可高亮主对象。

## 8. 预览页

每个技术点生成 `assets/预览.html`：把该技术点的全部 PNG 按顺序列出（`<figure><img src="name.png">` + 中文图注），自包含、无需网络。总览的图表放 `Overview-总览/assets/`。

---

## 9. 收尾（两件必做）

1. **清理 raw 抓取件**：删掉 `research/` 与 `assets/` 下的原始下载（网页 html、论文 pdf、`.src-*`、`.fetch.sh` 等）。**删除前先 `find` 出清单、确认是抓取件而非笔记**；笔记中的来源链接必须完整保留才可删。交付时报告"删了什么、保留了多少条链接"。
2. **维护总览**：更新 `<公司>-技术洞察总览.md`——
   - §一 一览表加一行：技术点 / **提出时间（arXiv v1）** / 编号与会议 / 一句话定位 / 最硬的一个数字 / 详细报告链接
   - §二 时间线图加节点
   - §三 逐项摘要：**每项 200–250 个中文字**（这是用户校准过的口径：给核心洞察 + 机制 + 数字 + 影响 + 一条边界/反证）
   - §四 横向对比、§五 系列关系（**查作者重叠**——同一批作者往往构成内部路线）、§六 未决事项

## 附：本环境常用命令与路径

```bash
# 论文正文（避免被工具截断：自己抽文本并分段打印）
curl -sL -A "Mozilla/5.0" https://arxiv.org/html/<id>v<n> -o /tmp/p.html
python3 - <<'PY'   # 去标签、压缩空白、按关键词切段打印
import re,html; s=open('/tmp/p.html',encoding='utf-8',errors='ignore').read()
s=re.sub(r'<(script|style)[^>]*>.*?</\1>','',s,flags=re.S); s=re.sub(r'<nav[^>]*>.*?</nav>','',s,flags=re.S)
t=html.unescape(re.sub(r'<[^>]+>',' ',s)); t=re.sub(r'[ \t\xa0]+',' ',t)
print('\n'.join(l.strip() for l in t.split('\n') if l.strip()))
PY

# arXiv 元信息（标题/提交历史/会议）——核实编号与 v1 时间
curl -sL -A "Mozilla/5.0" https://arxiv.org/abs/<id> | grep -A3 "Submission history"

# 仓库元信息与文件树
curl -s https://api.github.com/repos/<org>/<repo> | python3 -c "import json,sys;d=json.load(sys.stdin);print(d['stargazers_count'],d['created_at'],d['pushed_at'])"
curl -s "https://api.github.com/repos/<org>/<repo>/git/trees/main?recursive=1" | python3 -c "
import json,sys,re
d=json.load(sys.stdin)
[print(t['path']) for t in d['tree'] if re.search(r'关键词',t['path'],re.I)]"

# 引用数（Semantic Scholar；易 429，需退避重试；元数据接口比列表接口更稳）
curl -s "https://api.semanticscholar.org/graph/v1/paper/arXiv:<id>?fields=title,citationCount,influentialCitationCount,venue"
```

**注意**：`/tmp` 在部分环境**每次 bash 调用即清空**——所有"下载 + 解析"必须在**同一次调用**内完成。
